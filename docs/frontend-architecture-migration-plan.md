## 2. 文档分工

- `AGENTS.md`：强制项目规则，并要求架构任务先读取本文。
- 本文：master 维护公共约束与计划基线，开发分支追加当前阶段、验收门禁和执行结果；同步公共规则时不得抹去阶段进度。
- `README.md`：同步当前实际架构树、前端目标架构树、依赖边界和真实文件路径。
- `FINAL-PROMPT.md`：约束长期产品目标，不因本次目录迁移改变。
- 实际代码与测试：判断当前实现状态的唯一事实依据。

## 3. 全程约束

1. 公共规范、架构目标和迁移计划基线经授权提交到 `master`，再选择性同步到 `codex/frontend-contracts-yas-2026-0055`；架构阶段代码、测试和配套 README、本文执行记录、审计更新只在该开发分支提交。不在 master 实施架构阶段，不把阶段执行文档拆到 master 另交，不另建迁移分支，不自动合并回 master。
2. 每次只执行一个 `current` 阶段，不并行实施多个阶段，不提前处理后续模块。
3. 如需调整阶段顺序或范围，必须先获得项目负责人明确授权并更新本文。
4. 开发分支的 `src/contracts/` 已完成，不重复创建，也不因 master 尚未包含而复制到 master；只有实际数据契约存在差异时才单独报告和修正。
5. 迁移只改变代码组织、引用和必要的组合方式，不改变 UI、文案、样式效果、API 地址和字段、推荐算法、评分、错误语义、降级行为或存储 Key。
6. 不修改服务端、`public/`、`src/data/` 中的产品事实、核验记录和素材；仅允许更新指向这些文件的代码引用。
7. 不引入 Redux、TypeScript 全量迁移、新 UI 框架或新依赖。
8. 不创建没有实际职责的空目录、空文件或一次性抽象；组件拆分不应造成无意义的 props 转发。
9. 移动代码时同步更新引用和测试，不长期保留重复实现或无意义的转发导出。
10. 每阶段完成后必须同步本文状态、真实验证结果和 README“项目架构”的当前实际结构及相关路径。
11. 未经人工测试明确确认，不提交、不推送、不打标签；确认通过后按 `AGENTS.md` 13.2 在 `codex/frontend-contracts-yas-2026-0055` 提交并推送当前小步，不执行发布、强推或不可逆操作。
12. 不覆盖用户现有修改，不删除来源不明文件、历史证据或旧版备份。

开始修改以及提交、推送前，必须核对任务对应分支、HEAD、工作树、暂存区和远端状态。架构任务先 `git fetch origin master`，读取 `origin/master:AGENTS.md` 和公共规范章节，比较规则副本并记录规范来源 SHA；不能核验最新规范时只做只读检查。分支不符、本分支上游领先或与本分支分叉时先报告，不自动切换、清理、变基或强推。未提交修改、未跟踪文件与临时 stash 不算已建立的版本回退点，也不得以备份为由绕过人工验收擅自提交或丢弃文件。

## 4. 阶段状态与门禁

状态只使用以下四种：

- `pending`：尚未开始。
- `current`：当前唯一允许执行的阶段。
- `blocked`：存在阻塞，必须记录原因和下一步。
- `done`：代码、测试、页面回归和文档均已按阶段范围完成。

标记 `done` 前必须满足：

1. 本阶段实际修改已经落地，且没有提前实现后续阶段。
2. 相关测试已运行并通过；每次涉及代码的阶段都运行 `npm test` 和 `npm run build`。
3. 涉及用户界面的阶段已检查相关成功、失败和降级路径，以及一个常见桌面视口和一个 360px 级手机视口。
4. 浏览器控制台无新增未处理错误。
5. README 当前架构树、受影响路径和本文状态已经同步。
6. `git diff --check` 通过，交付中列明修改文件、真实验证结果和剩余风险。
7. 如已获授权提交，记录提交 SHA；未提交时明确写“未提交”，不得虚构 SHA。
8. 人工验收、阶段收尾记录及 `AGENTS.md` 12.1 要求的两份累计报告已经同步；无数据变化时写明无新增核验。最终状态纳入收尾提交，远端提交与阶段标签核验成功后，才可对外交付为“阶段已完成归档”。

## 5. 每阶段固定工作流

```text
fetch origin master，读取最新公共 AGENTS 与规范章节，必要时先处理选择性规范同步
→ 读取 FINAL-PROMPT.md、开发分支的本文和 README 项目架构
→ 核对固定分支、current 阶段、HEAD、工作树、暂存区、远端和相关源码
→ 分配 ARCH-XX-SNN 小步编号，记录问题或迁移原因、修改前 SHA、拟改文件和验证/回退范围
→ 小步移动或抽取代码并更新引用
→ 运行相关测试、npm test、npm run build 和 git diff --check
→ 更新本文与 README，但阶段保持 current
→ 交付项目负责人人工测试，不提交、不推送
→ 人工确认通过后复核实际 diff；阶段收尾小步同时把最终状态和验收记录纳入待提交文档
→ 只暂存本步文件，检查暂存差异并提交、推送 codex/frontend-contracts-yas-2026-0055，核对远端 SHA
→ 阶段内仍有小步则继续；完整阶段验收通过后，在收尾提交上建立带注释的 arch-stage-XX 标签
→ 推送并核对远端标签指向，在交付中记录真实 SHA/tag，下一次文档同步回填而不改写历史
```

### 5.1 提交、标签与回退门禁

- 一个提交只处理一个可独立构建、验证和回退的小步，不夹带其他阶段或无关修改。
- 每小步使用唯一的 `ARCH-XX-SNN` 编号，按阶段从 S01 递增且不复用；提交的问题描述同时带 `[ARCH-XX]` 和小步编号，继续遵守 `【问题】… 【修改】…` 格式，已有 YAS 编号时同时记录。
- 自动验证未通过时不得交付人工验收；人工验收未明确通过时不得提交、推送或标记 `done`。
- 人工测试确认是对当前小步提交并推送 `codex/frontend-contracts-yas-2026-0055` 的授权，不代表可以提前进入下一阶段。
- 每个完整阶段使用带注释的唯一标签 `arch-stage-00` 至 `arch-stage-11`，指向包含最终状态与验收记录的人工确认收尾提交；注释写明阶段、小步编号、验证摘要和提交 SHA，标签一旦推送不得复用或移动。
- 阶段内小步不必分别打标签，但每个提交都必须能独立构建和回退。
- 回退公共代码优先使用 `git revert <sha>`。先保护工作树、确认故障提交及后续依赖，按从新到旧的顺序撤销必要范围；有冲突先报告并解决，不强推或硬重置。回退后重新运行相关测试、构建及必要页面回归，追加故障现象、复现步骤、原 SHA、反向提交 SHA 和结果，保留原历史、阶段标签和失败证据；实际回退与推送仍须取得项目负责人授权。
- 纯文档变更以人工核对路径、链接、状态和规则一致性作为人工验收，不伪造页面测试结果。
- 人工确认仅对应已验收的 diff；新增实质修改后重新验证并确认。未完成本阶段验收时，不以某个小步通过为由自动推进下一阶段。
- 推送后用 `git ls-remote --heads origin refs/heads/codex/frontend-contracts-yas-2026-0055` 核对实际远端 SHA；阶段标签用 `git ls-remote --tags origin 'refs/tags/arch-stage-XX*'` 同时核对标签对象和 `^{}` 指向的提交。失败时记录待推送/待标签，不把本地对象存在等同于远端已备份。
- 每小步记录修改前的已验收基线和修改后的实际提交；阶段收尾按 `AGENTS.md` 12.1 追加 `docs/stage-delivery-test-report.md` 与 `docs/product-data-accuracy-audit.md`。尚未提交的改动只在工作树中保留，Git 不恢复浏览器数据、环境变量或外部服务状态。
- 公共规范提交在 master 取得明确授权后执行；开发分支同步时只选择该文档提交，记录来源 master SHA，不整支合并 master 的其他回退或无关变更。阶段进度与验收记录保留在开发分支，下一次任务先核验最新公共规范。
