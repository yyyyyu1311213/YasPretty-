## 阶段 0：仓库安全与基线

### 这个阶段是做什么的

阶段 0 不增加产品功能，而是先回答“项目当前到底有什么、能否运行、哪些内容不能公开”。它为后续开发建立安全边界和可复查基线，避免把真实密钥、本地对话、构建产物或未授权图片带入 Git、比赛材料和公开版本。

### 实际完成内容

- 建立 `.gitignore`，排除 `node_modules/`、`dist/`、浏览器 QA 目录、本地工作记录、服务端记忆、`server/key.txt` 和待核验图片目录。
- 建立 `.env.example`，只保留配置项名称和安全示例，不包含真实凭据。
- 建立 README 基础版，记录真实功能、运行方法、隐私边界、第三方能力和未实现事项。
- 扫描仓库中的常见密钥、隐私数据、临时目录和公开素材风险。
- 移除旧版 `beauty-assistant.html` 中的一枚硬编码智谱凭据；没有在文档或测试输出中复制该凭据。
- 盘点 31 条底妆数据的类别、稳定 ID 和旧页面必需字段。
- 核对目标数据字段，确认 `priceVerifiedAt`、`imageSource`、`informationSources` 和 `verificationStatus` 当前均为 0/31。
- 明确 `rating` 和 `metrics` 是没有用户样本支撑的编辑示例，禁止描述为真实用户统计。
- 明确本地产品图片、品牌图片和远程占位图片尚未形成授权台账，不能进入公开版本。
- 记录 React 主站、历史 Node 服务、现有页面功能和生产构建的事实基线。

详细记录见 [阶段 0：仓库安全与基线](phase-0-baseline.md)。

## 阶段 1：生产级 AI 网关

### 这个阶段是做什么的

阶段 1 将原先由浏览器持有第三方 Key、直接拼装上游请求的链路，迁移为 YasPretty 服务端统一编排。它解决密钥暴露、输入缺少约束、错误直接外泄、接口无限调用以及外部服务失败时主流程不可用的问题。

本阶段仍服务于现有小Y，不负责生成阶段 2 所定义的结构化完整妆容方案。

### 实际完成内容

- 使用 Fastify 建立统一服务端入口，开发时由 Vite 代理，生产构建由同一个 Node 服务提供页面和 API。
- 提供 `GET /api/health`、`GET /api/weather` 和 `POST /api/assistant`。
- 将智谱 GLM、智谱 `web-search-pro` 和 Open-Meteo 分别封装为服务端 provider。
- 智谱 Key 只从服务端 `ZHIPU_API_KEY` 环境变量读取，普通用户界面不再显示或接收 API Key。
- 移除前端 Authorization 拼装和旧代理调用；旧 `/proxy/*` 与 `/memory*` 返回 410，防止继续误用。
- 使用 Zod 校验请求、画像、天气响应、模型响应和可见来源。
- 将请求体限制为 64 KiB，并限制消息数量、文本长度和画像字段。
- 为智谱请求增加 20 秒默认超时及一次受限的临时故障重试。
- 增加每 IP 分钟限流和单进程 AI 每日额度。
- 使用 Helmet 增加安全响应头；生产接口不返回无条件跨域通配头。
- 建立稳定公开错误码，不返回堆栈、服务器路径、上游原始响应或密钥。
- 收紧日志内容，不记录请求体、Authorization、完整查询或用户画像。
- 将联网搜索结果作为不可信资料隔离，网页文本不能覆盖系统规则。
- 小Y画像和最近对话迁移到版本化浏览器存储，并清理两个旧版 AI 配置键。
- 保留站内本地规则推荐，并增加肤质、预算硬过滤以及模型产品 ID 白名单。
- 增加 API、provider 和小Y核心规则自动化测试。

详细架构与错误行为见 [阶段 1：生产级 AI 网关](phase-1-ai-gateway.md)。

### 对用户需求的价值

- 普通用户不需要申请、理解或粘贴第三方 API Key，避免误操作和凭据泄露。
- 用户可以直接在 YasPretty 主站使用小Y，前端只与 YasPretty 自身 API 通信。
- 没有智谱 Key或模型暂时不可用时，产品浏览、本地规则推荐和天气仍然可以使用，不会把整个应用变成不可用状态。
- 用户提出预算和肤质要求时，站内推荐会先执行确定性硬过滤，减少明显违反条件的结果。
- 模型返回不存在的产品 ID 时，界面不会展示虚构商品。
- 天气回答由 Open-Meteo 提供来源；联网或模型失败时会明确提示，而不是伪装成功。
- 请求过大、格式非法或调用过频时，服务会给出稳定错误，降低滥用对其他用户的影响。
- 匿名画像和最近对话继续保存在当前浏览器，不会被描述成服务端永久保存。

### 用户体验路径

1. 启动项目后访问 `http://127.0.0.1:5174/`。
2. 从主站进入小Y，无需配置 API Key 或模型。
3. 输入肤质、预算或底妆需求，可获得站内本地推荐。
4. 查询城市天气时，由 `/api/weather` 返回 Open-Meteo 数据和来源。
5. 服务端配置有效 `ZHIPU_API_KEY` 后，可使用模型对话和需要联网检索的问题。
6. 未配置 Key 时，模型请求明确降级；产品库、本地推荐和天气仍可继续使用。

生产构建完成后，也可以通过 `http://127.0.0.1:8787/` 验证 Fastify 同源页面与 API。

## 阶段 2：结构化妆容方案

### 这个阶段是做什么的

阶段 2 把“聊天式推荐”推进为可验证的妆容决策流程：先收集结构化条件，再执行确定性硬过滤和可解释评分，最后生成可以逐步执行、可以打开站内产品详情、也可以明确指出资料缺口的 `MakeupPlan`。本阶段的完整方案不依赖照片，用户不上传照片也能完成流程。

### 实际完成内容

- 在服务端集中建立 `UserProfile`、`MakeupRequest`、`PlanStep`、`CandidateEvidence` 和 `MakeupPlan` Zod schema。
- `UserProfile` 覆盖自述肤质及来源、色调倾向、妆效偏好、预算、熟练度、排除品牌、敏感项和城市。
- `MakeupRequest` 覆盖场景、风格、带妆时长、时间、天气开关、照片开关和优先目标。
- `MakeupPlan` 覆盖输入快照、天气调整、7 个步骤、候选 evidence、产品 ID、置信度、限制、来源模式、创建时间和 schema 版本。
- 新增 `POST /api/makeup-plans`，最终响应再次通过 `makeupPlanResponseSchema` 校验。
- 新增确定性候选筛选：预算、肤质、妆效偏好和排除品牌作为硬条件；场景、带妆时长、色调和预算余量形成可展示评分依据。
- 每个候选保留 `matchedConditions` 和 `tradeoffs`，用户可以查看为什么入选以及需要自己复核的取舍。
- 本地模板生成 7 步方案：妆前、底妆、局部遮瑕、定妆、眉眼、腮红和唇妆。
- 对没有已核验站内产品的眉妆、眼妆、腮红和唇妆，只输出手法与颜色方向，不创造商品、价格或色号。
- 服务端有智谱 Key 时才尝试结构化模型输出；模型输出先提取 JSON、通过 draft schema、校验候选 ID 和硬条件，失败最多进行一次结构修复。
- 模型未配置、上游失败、JSON 无法解析或产品 ID 不在候选集时，自动回退到本地规则模板。
- 在小Y原有主站中加入妆容工作台：结构化需求采集、生成状态、错误状态、方案步骤、产品详情入口、候选证据和边界说明。
- 工作台明确照片分析尚未接入；当前 `photoEnabled` 固定为 `false`，不会上传或保存照片。

### 对用户需求的价值

- 用户不必先学会如何提问，可以直接填写肤质、妆效、场景、风格、预算和带妆时长。
- 用户修改预算或妆效后重新生成，硬条件会作用于候选集，不会只改变一段自然语言。
